Client-Side Encryption for Static Sites: pagevault + cryptoid

February 13, 2026 7 min read Updated: February 16, 2026
pagevault cryptoid encryption static-sites python web-crypto open-source hugo

I run a static site on GitHub Pages. No backend, no server, no database. That simplicity is the whole point — until you want to share something semi-private.

Maybe it’s client-confidential notes mixed in with public documentation. Maybe it’s solutions to homework problems that should be behind a password. Maybe it’s personal thoughts in a blog post that you want to share with specific people but not the entire internet.

The usual answer is “add a backend.” But I didn’t want to give up static hosting just because a few paragraphs needed a password.

So I built two tools: pagevault for encrypting HTML files and embedded assets, and cryptoid for encrypting Hugo markdown content at build time. They share the same cryptographic foundation but solve different problems.

Two Tools, One Crypto Core

Both tools use identical encryption:

  • AES-256-GCM (authenticated encryption)
  • PBKDF2-SHA256 with 310,000 iterations
  • v2 format with content-encryption-key (CEK) wrapping for multi-user support
  • Web Crypto API for browser-side decryption — no JavaScript crypto libraries

The difference is what they encrypt and when:

pagevaultcryptoid
EncryptsHTML regions, files, entire sitesHugo markdown body content
WhenPost-build (operates on HTML output)Pre-build (operates on markdown source)
AssetsImages, PDFs, audio/video embedded in ciphertextText only (assets served publicly by Hugo)
OutputSelf-contained HTML filesHugo shortcodes with ciphertext
RenderingContent is already HTML — just injectMarkdown rendered in browser via marked.js

Use pagevault when you need to protect complete documents with embedded assets — encrypted PDFs, image galleries, entire mini-sites. Use cryptoid when you have a Hugo blog and want some posts or sections behind a password while keeping the full Hugo workflow (taxonomies, related posts, RSS, etc.).

pagevault: Encrypt Anything, Serve Anywhere

pagevault encrypts regions of HTML files — not the whole page, just the parts you mark. Public navigation, styling, and scripts remain untouched. Only the sensitive sections become ciphertext, replaced with a password prompt that decrypts in the browser.

<header>Public navigation stays visible</header>

<pagevault hint="Contact me for the password">
  <h2>Private thoughts on this topic</h2>
  <p>This section is encrypted with AES-256-GCM...</p>
</pagevault>

<footer>Public footer stays visible</footer>

After running pagevault lock, the <pagevault> block becomes an opaque blob of base64. Visitors see a styled password prompt. If they have the password, the content decrypts instantly in their browser. If they don’t, they see nothing — not even the size of what they’re missing (with the --pad flag).

The output is a single self-contained HTML file. No JavaScript CDN, no external CSS, no runtime dependencies. You can email it, upload it to any static host, or open it from a local filesystem. Everything needed for decryption is embedded in the file.

Beyond HTML: Encrypting Arbitrary Files

pagevault wraps non-HTML files into encrypted HTML payloads:

pagevault lock report.pdf              # → _locked/report.pdf.html
pagevault lock presentation.pptx       # → _locked/presentation.pptx.html
pagevault lock mysite/ --site          # → _locked/mysite.html

The encrypted HTML includes the file’s contents as a base64 payload. When decrypted in the browser, a viewer plugin renders the content inline — images display as images, PDFs render in an embedded viewer, Markdown gets formatted with headings and code blocks.

After entering the password, the viewer renders the content with a toolbar showing the filename, file size, and a download button:

Seven viewers ship built-in: Image, PDF, HTML, Text, Markdown, Audio, and Video. Custom viewers follow the same plugin API — point viewers_dir at a directory of Python files and they’re discovered automatically.

The Closure Property

My favorite design constraint: the output of pagevault lock must be valid input to pagevault lock.

This means you can encrypt a page for Alice, then encrypt different sections of the same page for Bob, and everything just works. Alice sees her content. Bob sees his. The page round-trips cleanly through multiple encryption passes.

Composability replaces configuration. You don’t need pagevault to understand access levels — you just run it twice with different passwords on different sections.

cryptoid: Native Hugo Encryption

cryptoid takes a different approach. Instead of operating on HTML output, it works directly with Hugo’s markdown source files. You mark content for encryption in front matter, and cryptoid handles the rest.

---
title: "Confidential Project Update"
encrypted: true
groups:
  - team
  - leadership
password_hint: "Use your team credentials"
remember: ask
---

## Q4 Results

Revenue grew 23% quarter-over-quarter...

Running cryptoid encrypt replaces the markdown body with a Hugo shortcode containing encrypted ciphertext. Hugo then builds the site normally — the shortcode renders a password form, and the browser-side JavaScript handles decryption.

Hugo-Native Workflow

Because cryptoid operates at the source level, encrypted posts are still full Hugo citizens:

  • Taxonomies work — tags, categories, and series still render from front matter
  • Related posts work — Hugo’s content matching sees the front matter
  • RSS works — feeds include the post metadata (body is just the shortcode)
  • _index.md cascade — set encrypted: true in a section’s index and all children inherit it
  • Group-based access control — assign user groups in front matter, cryptoid resolves which users get key blobs

The CLI manages the full lifecycle:

# Setup
cryptoid init                                    # interactive config setup
cryptoid config add-user bob --group team        # manage users and groups

# Protect content
cryptoid protect content/private/ --groups team  # mark directory for encryption
cryptoid encrypt --content-dir content/          # encrypt all marked files

# Manage
cryptoid status --content-dir content/           # show encryption status
cryptoid rewrap --content-dir content/           # update key blobs after user changes
cryptoid decrypt --content-dir content/          # restore plaintext for editing

Cascade Resolution

Encryption settings propagate from _index.md files downward. If a file’s own front matter has encrypted: true, that’s used. Otherwise, cryptoid walks up parent directories checking each _index.md — the nearest one with an encrypted field wins.

This means you can protect an entire section with one line in _index.md, then override individual files with encrypted: false if needed.

Shared Cryptographic Design

Both tools share the same v2 encryption format and key-wrapping model.

CEK Key-Wrapping

A random content-encryption key (CEK) encrypts the actual data once. The CEK itself is then wrapped (encrypted) separately for each user’s derived key:

Content  ──encrypt with CEK──>  Ciphertext (one copy)
CEK  ──wrap with Alice's key──>  Key Blob A
CEK  ──wrap with Bob's key────>  Key Blob B

Adding a user wraps one small key blob. Removing a user deletes one key blob. The bulk content stays untouched. Both tools provide a sync/rewrap command for key management, and --rekey for full CEK rotation.

PBKDF2 Secret Format

Both tools derive the wrapping key from "username:password" — a single PBKDF2 derivation per login attempt. The browser tries each key blob until one unwraps successfully, revealing the CEK.

Threat Model

Both tools protect against the same threats: casual snooping (scrapers, search engines, curious visitors) and offline brute-force attacks. AES-256-GCM with 310k PBKDF2 iterations makes dictionary attacks expensive.

Neither defends against browser-level adversaries (malicious extensions, XSS on the same origin) or a hosting provider modifying served files. The model is “your static host is honest but the public internet is not.” For static hosting, that’s the right tradeoff.

When to Use Which

Use pagevault when:

  • You need to encrypt non-Hugo HTML pages or files
  • Images, PDFs, or other assets must be protected (embedded in ciphertext)
  • You want self-contained encrypted files you can email or host anywhere
  • You need the closure property (composable multi-tier encryption)

Use cryptoid when:

  • You have a Hugo site and want password-protected posts or sections
  • You want encrypted content to participate in Hugo’s taxonomy, search, and RSS
  • Text content is the primary concern (images can remain public)
  • You want directory-level cascade (_index.md inheritance)

Use both when:

  • Your Hugo site has some protected markdown posts (cryptoid) and also serves encrypted file downloads (pagevault)
  • You want public blog posts with embedded encrypted attachments

Try Them

# pagevault
pip install pagevault
pagevault config init
pagevault mark page.html -s ".private"
pagevault lock page.html

# cryptoid
pip install cryptoid
cryptoid init
cryptoid protect content/private/ --groups team
cryptoid encrypt --content-dir content/
cryptoid hugo install  # install shortcode + JS into your Hugo site

Both projects are on GitHub (pagevault, cryptoid), MIT-licensed, and designed as building blocks — composable, self-contained, no server required.

Static sites shouldn’t need backends just because some content needs a password.
